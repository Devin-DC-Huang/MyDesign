最近在业务的流程中使用 agent，尤其是在数据采集的业务中使用 agent 的经验。已经看过很多人在分享 agent 架构、agent 怎么接知识库等等，但 agent 怎么在传统的业务上接入、发挥出作用，接地气的比较少。同时最近的实践也让我更深入地了解到，完全依赖向模型许愿，是没法做到很好的效果的。

先说背景，这是一个采集开源信息的项目，比如开源社区的 maintainer、license、官网地址、文档地址等。就选 maintainer 来说吧，在社区里它通常是一个 yaml 或者 md 文本，或者是官网的 html。如果是 yaml，都有对应的格式；至于 md 和 html 就比较自由，但一般大的社区都会有固定的格式，小的或者个人开源项目，就是散文式的描述。

找 maintainer 主要分为两部分，一个是找正确的链接，一个是解析链接里的内容。找链接的话，借助成熟的搜索工具基本上都能找到，只是有噪音（比如那个名单只是标题看起来像，里面内容并没有 maintainer 人员名单）。然后就是解析。

最开始，识别的方式就是丢一个 prompt，让大模型自己去抽取。这里最大的缺陷就是：一个是幻觉，常常出现名单上不存在的人；另一个是漏人，因为很多时候名单是藏在大篇幅的散文里面的那么几个名字，必须得全文读完，文本一大，输出的名单常常就会很少。

于是做了一些改进。一个是拆分为找链接和解析两步，这两个环节都让大模型自己 review 一次。找链接的过程还是没有什么改善。至于解析文本的环节，让大模型自己根据上下文的格式生成脚本，生成脚本之后，再由程序执行、输出结果，再用 LLM review 一次。至于提升呢，也不能说没有，只能说没啥作用。幻觉是没了，但缺斤少两的问题依然存在，因为 review 的时候依然是大模型自己去抽取，这个时候还是会缺斤少两。后来就暂停了优化，因为有其他项目更紧急。

最近重新思考了一下问题的本质。假如我去看一份 maintainer 的名单，我会怎么判断呢？你们可以想下自己读文本是怎么去理解和读的。如果是 yaml，那基本就是看它的形式，看每个字段的含义，然后选取社区 maintainer 身份对应的字段。如果是文本，一般会看整体格式，基本都是按标题、章节一段段去看，每一段的标题基本说明了这一段是什么内容。如果是表格形式，就是看表格的表头，再看表格内容。

所以这个事情，是可以交给 agent 去做吗？为什么？

本质的本质就是：这首先是开源社区写出来的，目的就是为了让大多数人能无歧义地读懂，当然这需要对开源社区有一定的知识（但是不多），所以 agent 大概率是能读懂的（准确率 90% 是我自己瞎拍的，我自己去看也差不多，有时候有些奇怪的 title 需要额外查）。

那还有 10% 怎么办呢？既然是大多数人的共识，agent 大概率也行，那就多加几个 agent，相互打架、相互协商。多个独立的链路都做同一件事，如果大概率是有共识的，就相互把自己的答案丢给对方，基本就能协商出一个结果。如果还不行，说明大家都不懂，如果我自己上手，估计也要找资料，那就人来兜底。为了让结果更精确、更可控，需要拆分步骤，而不是一个大而全的。我自己实践的经验是这样的，包括自己干活也是按步骤来。

新的大体方案就是：

1、找链接：
直接把搜索工具给 agent，核心就是写好 prompt。

2、解析链接：
a. 先判断链接内容是否值得解析，就是是否有名单（两路 agent 相互校验，互喂对方答案，最多三轮协商）；
b. 看文本的格式是什么，是 yaml、散文还是表格，三套 prompt 选一个（两路 agent 相互校验，互喂对方答案，最多三轮协商）；
c. 基于 prompt 写脚本（两路 agent 相互校验，互喂对方答案，最多三轮协商）。

目前这个流程跑下来，准确率很高。最后没有协商成功的，我去分析，确实需要一些额外的知识。

从这个过程中，我觉得核心经验有几点：

1. 本质中的本质：你的问题答案是千人千面，还是大概率能达到共识。如果是千人千面，那么用 agent 也得不到答案。
2. 数据，数据，还是数据。这个优化的过程中，我看了很多 maintainer 的文件，才能形成多个 prompt 的经验。原来只有一个 prompt，怎么调效果都不稳定；后来发现形式也很重要，就分成 3 个 prompt，成功率一下子上去了。还是要让 agent 一次做一件简单的事情。
3. 目前还是依赖 prompt，没法直接丢原文、直接许愿要结果。调试的重点就是小步快跑，快速原型验证，验证通过再接入主流程，然后再持续迭代每个环节。
4. 剩下的就是持续运营、做好监控。监控好 agent 无法判断的内容，可以基于数据给一些项目定制化的 prompt。
5. 最后就是成本、性能，把能够确定性的内容固化下来，不再交给 agent。比如拉取 html，先简化变成文本格式等等。也可以把其中一个 agent 生成的脚本固化下来，把成功的那一次脚本保存起来，下一次只跑一次 agent 生成，有分歧再重新调整，基本就可以自进化了。

流程设计好之后，更多的时间还是在确定性的规则和 prompt 之间调整，这只是个体力活。每个领域有各自的 prompt，你得承认，对业务理解深浅严重影响 prompt 的质量。

就目前来看，agent 还远不能代替我，很多步骤在开发过程中都是尽可能简化成确定性的步骤，而且有些环节根本不会触发，或者触发了也可接受，agent 常常会过度优化。但是确实提升了效率，不是写代码的效率，基本上 agent 生成的代码我都改了好几版才上库，提升的是业务的效率。没有 agent，这个功能几乎无法做出来，不可能每个社区定制一套规则。
